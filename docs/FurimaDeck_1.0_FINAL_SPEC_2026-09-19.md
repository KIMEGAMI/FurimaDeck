- 既存の仕入・販売・会計データを削除・初期化しない。既存DB構造を再利用し、新しい仕入データ正本を追加しない。

# 2. 製品定義

FurimaDeckは、

> **小規模店舗・個人せどり事業者が、商品・在庫・出品・売上・利益・確定申告用データを一元管理し、自分自身の販売実績から「何が儲かるか」「どこで売るべきか」「どの商品を改善すべきか」を判断できる販売管理・経営分析SaaS**

である。

FurimaDeckは単なる在庫管理アプリではない。

最終的な価値は、

- 管理する
- 数字を把握する
- 問題を見つける
- 次の販売行動を判断する
- 確定申告へつなげる

までを一つのサービスで行えることに置く。

既存機能を維持し、デグレードさせない。

必須:

- 商品登録

- 現在庫数量

- 商品属性
- 管理ID / SKU

- メモ
- 複数画像
- 画像並び替え
- 画像削除

全商品は必ずログインユーザーに帰属し、他ユーザーのデータを参照・更新・削除できない。

### 商品IDと数量の単位（1.0確定仕様）

- 1つの商品IDは、個体を識別できる現物1点を表す。
- 同型・同タイトルの商品を複数仕入れた場合も、現物ごとに別の商品IDを登録する。
- 仕入数量・出品数量・販売数量は各商品IDにつき1。現在庫は0または1とする。
- 複数数量の一括仕入、複数数量を1商品IDへまとめる管理、部分販売は1.0の対象外。
- 返品・在庫調整は同じ個体の商品IDの在庫を0または1の範囲で更新する。

### 仕入情報と在庫履歴の管理場所

- 商品登録時に仕入日・仕入単価・仕入送料・その他仕入費・仕入先を登録できる。
- 商品編集画面では、編集可能な状態の仕入情報を商品本体と一緒に更新する。
- 仕入情報が変更された場合は、変更前後をイベント履歴へ記録し、変更と履歴記録を同じDBトランザクションで確定する。
- 販売または会計照合で履歴保護が必要な場合は、仕入情報の変更を拒否し、商品名など他項目だけが部分更新されることも防ぐ。
- 会計画面は商品に紐付く現在の仕入情報と必要な履歴を参照する。会計画面を独立した仕入情報の登録・編集場所にしない。
- 在庫数量は商品IDあたり0または1。通常の商品編集と仕入情報編集では変更できず、理由を伴う在庫調整または販売・取消・返品イベントで更新する。

# 10. 金額計算の原則

## 10.1 実利益

FurimaDeck内部の実利益は、既存の正式Calculator / Sale作成ロジックを唯一の正として使用する。

概念式:

```text
実利益
= 売価
- 原価
- 販売手数料
- 販売送料
- 仕入関連費
- 梱包費
- 修理費
- クリーニング費
- その他費用
- 返品等の確定損失
```

分析画面、CSV、会計連携側で別の利益計算を再実装しない。

## 10.2 実利益率

```text
実利益率 = 実利益 ÷ 売価 × 100
```

売価0の場合は0またはN/Aとして安全に処理し、ゼロ除算しない。

## 10.3 税務上の利益との区別

FurimaDeckの「実利益」は経営管理上の指標である。

税務上の所得、棚卸、必要経費、仕訳上の利益と同一であると断定しない。

# 13. 高度分析

## 13.1 平均販売日数

Saleに紐づくListingの `listed_at` とSaleの `sold_at` を使用する。

```text
販売日数 = sold_at - listed_at
```

- 同日販売は1日扱いとして利益速度のゼロ除算を防止する。
- `listed_at` または `sold_at` がないデータは日数分析から除外し、「算出対象外件数」を表示する。
- 別商品や別Listingの日付で補完しない。

表示:

- 平均
- 中央値
- 最短
- 最長
- 対象件数

中央値を主要指標として優先表示する。

## 13.2 滞留在庫分析

対象:

- `in_stock`
- `listing_ready`
- `listed`

原則として `reserved`, `out_of_stock`, `archived` は通常の滞留在庫から除外する。

仕入日を基準に以下のバケットで表示する。

- 0～29日
- 30～59日
- 60～89日
- 90日以上

`purchase_date` がない商品は「仕入日未設定」として別集計し、created_atで勝手に代用しない。

## 13.3 在庫資金分析

現在庫に寝ている仕入資金を可視化する。

1.0の基本指標:

```text
現在庫仕入額 = Σ（仕入単価 × 現在庫数量）
```

表示:

- 現在庫仕入額
- 30日以上
- 60日以上
- 90日以上
- 仕入日未設定

「90日以上の在庫に○円の仕入資金が滞留」のように表示する。

## 13.4 販売消化・在庫回転分析

曖昧な単一「在庫回転率」だけで評価しない。

FurimaDeck 1.0では、

- 平均 / 中央販売日数
- 滞留日数
- SOLD件数
- 現在庫数
- 販売消化率
- 利益速度

を組み合わせて回転性を判断する。

販売消化率の分母・分子は実装時に対象期間と在庫コホートを明示し、画面ヘルプにも定義を出す。

定義を後から変更した場合はテストと表示文言も同時に更新する。

# 15. 利益速度

FurimaDeck独自の経営補助指標として実装する。

```text
利益速度 = 実利益 ÷ max(1, 販売日数)
```

単位:

`円 / 日`

例:

```text
商品A: 10,000円利益 / 90日 = 約111円/日
商品B:  4,000円利益 / 10日 = 400円/日
```

用途:

- 利益だけ高いが長期滞留する商品
- 利益は中程度でも高速回転する商品

を区別する。

利益速度は税務指標ではなくFurimaDeck独自の経営分析指標として明記する。

# 16. 利益率 × 回転速度マトリクス

商品・ジャンル・ブランド・仕入先について、

```text
                         回転が速い            回転が遅い

利益率が高い             最重要ゾーン          高利益・長期型

利益率が低い             回転型                改善・縮小候補
```

として可視化する。

高低判定は固定の恣意的閾値ではなく、原則として選択期間内のユーザー自身の中央値 / 分位点を基準にする。

母数が少ない場合はマトリクス評価を行わず「データ不足」とする。

# 17. 出品先適性分析

目的:

> 同じ種類の商品を、過去の自分の実績ではどこで売ると「利益」または「回転」が良かったかを示す。

外部サイトの市場価格を勝手に推測しない。

ユーザー自身のFurimaDeckデータだけを根拠とする。

## 17.1 比較軸

出品先ごとに、

- 対象SOLD件数
- 中央売価
- 中央実利益
- 中央実利益率
- 中央販売日数
- 利益速度

を表示する。

## 17.2 判定

比較可能なデータが各候補で最低3件以上あることを基本条件とする。

不足時:

`分析に必要な販売実績が不足しています`

と表示する。

表示例:

```text

→ 過去実績ではYahoo!フリマの中央値が高い

回転を重視する場合
→ 過去実績ではヤフオクの販売日数中央値が短い
```

「必ずここで売れる」等の断定は禁止。

根拠数値とサンプル件数を必ず併記する。

# 22. 価格見直し候補

自動値下げはしない。

ユーザーが判断するための参考データを提示する。

価格見直し候補の基本条件:

- 長期滞留している
- 同じカテゴリ / ブランド等の比較可能SOLD実績が十分ある
- 現在出品価格がユーザー自身の過去実績から大きく外れている

価格比較は最低5件の比較データを基本とする。

表示:

- 現在価格
- 比較サンプル数
- 過去売価中央値
- 過去売価の参考レンジ
- 過去販売日数中央値

`価格見直しの参考`

# 24. 出品先変更候補

`出品先変更を検討`

- 現在60日以上滞留

- 別出品先の販売日数中央値が20%以上短い、または十分な差がある

ただしサンプルが少ない場合は候補を出さない。

# 65. FurimaDeck 1.0の最終差別化

FurimaDeckは、

> **「何を売ったかを記録するソフト」ではなく、「何が儲かり、何が滞留し、次に何を改善すべきかを自分の販売実績から教えてくれる販売管理SaaS」**

を目指す。

差別化の中心は、

1. 確定申告までつながる販売データ
2. 高度な利益・回転分析
3. 販売改善アクション
4. 小規模事業者でも理解できる説明可能な数値
5. 外部サービス規約に依存しない安全な分析

である。
