## 1. 決定済みの要求

ユーザーが確定した正式仕様:

- 仕入単価・仕入数量・仕入先は商品管理から登録・編集する。
- 現在庫は入出庫履歴に基づいて管理し、通常の商品編集では直接変更しない。
- 追加仕入、単価変更、仕入先変更の履歴を保持する。
- 会計画面は仕入情報を参照し、原価・利益・仕入支出を集計する。
- 商品管理と会計画面に独立した仕入データを持たせない。
- 既存の仕入、販売、会計データを削除・初期化しない。
- 商品登録、追加仕入、販売、返品、在庫調整、利益計算を検証する。
- DB変更が必要な場合は、変更内容・既存データへの影響・移行・切り戻し方法を実装前に提示する。
- 1商品IDはユニークな現物1点を表す。同じ型番の複数個体は別商品IDとし、仕入・販売・現在庫数量を複数個体の合算として扱わない。
- 販売原価は対象商品ID自身の仕入原価に紐付け、異なる商品ID間の平均・FIFO配賦をしない。

本書はこの決定をコード変更へ進めるための設計案である。DB変更に関するユーザー指示は、影響と移行・切り戻しの提示を実装前に行うことを求めている。

## 2. 初回監査時点（2026-11-05）の実装差分

以下は設計提案を作成した初回監査時点の記録である。後続の実装経過は本書末尾の日時付き記録を優先し、この節の過去形・未実装記述を現在状態として解釈しない。

- `products` に `purchase_date`, `purchase_unit_cost`, `purchase_quantity`, `quantity_available`, `purchase_shipping_cost`, `other_purchase_expense`, `supplier_id` がある。
- 商品登録・編集の `ProductController` は、仕入情報と通常の在庫数量をフォームから受け取らない。
- `FurimaDeckAccountingProductController` が会計画面から商品単位の仕入情報を更新する。販売や会計明細がある商品は変更が制限されている。
- `SaleLifecycleService` は販売時に商品数量を直接減らし、取消・返品時に直接増やす。
- 外部売上CSV取込も `quantity_available` を直接減らす。
- 販売時の原価は `sales.cost_basis` に保存済みのスナップショットを持つ。
- `accounting_entries` の仕入行は現在 `user_id + entry_type + product_id` の一意制約で商品ごとに1件だけである。1商品IDが現物1点という確定仕様では、この制約は自然であり、複数個体分の仕入行を同一商品IDへ追加するために変更してはならない。
- 仕入会計明細には証憑・税区分・外部取込/連携状態・外部ID・照合記録が結び付く。仕入情報の変更履歴はイベント台帳で保持し、既存会計明細・同期履歴・外部ID・照合状態を上書きしない。
- 会計ワークフローのFeatureテストは、商品登録・編集で仕入情報を変更できない現仕様を期待している。

## 3. 現行の正本と責務

既存の`products`レコードを、商品IDに紐付く現在の仕入情報（仕入日、仕入単価、仕入送料、その他仕入費、仕入先）の唯一の正本とする。仕入情報の登録・編集は商品管理画面から行い、会計画面は同じ値を参照・集計する。仕入用の別テーブルや会計画面独自の仕入値を作らない。

`product_inventory_events`は現物単位の在庫残高を追跡し、仕入情報の変更前後を暗号化スナップショットで記録する。イベントスナップショットは監査履歴であり、仕入現在値の別正本ではない。`products.quantity_available`および`inventory_status`は在庫イベント残高と同一トランザクションで同期する互換投影値である。通常の商品編集で現在庫を直接入力しない。

商品IDごとに現物1点を表し、同型の別個体は別の商品IDとする。追加で現物を仕入れる場合は新しい商品IDを作る。仕入情報変更は数量変化なしの履歴イベントとして記録する。確定販売・保護対象の会計照合がある場合は変更を拒否し、商品名など他項目だけの部分更新も許さない。販売原価スナップショットと既存会計・外部連携履歴は変更しない。

| イベント | 数量変化 | 追加情報 |
|---|---:|---|
| 初回仕入・移行時残高 | +1（移行時残高イベントは現在庫0または1） | 仕入日、取得原価、仕入先、証憑情報 |
| 仕入情報の訂正・変更 | 0 | 変更前後の仕入単価・仕入先・日付・証憑情報、操作者、理由 |
| 販売 | 0または-1 | 既存Saleへの参照、販売時原価スナップショット |
| 取消・返品再入庫 | 0または+1 | 元Saleへの参照、理由、元販売原価 |
| 在庫調整 | -1、0または+1（調整後残高は0または1） | 理由、操作者、調整前後の状態 |

商品IDごとに商品は一意な現物1点を表す。同じ型番でも個体が違えば別商品IDとする。1つの商品IDの在庫残高は常に0または1である。商品管理・会計集計・分析は同じ`products`仕入現在値を使い、仕入変更履歴と在庫変化の検証に`product_inventory_events`を使う。商品管理と会計画面に独立した仕入記録は残さない。

販売記録と外部売上CSVの二重取込を防ぐため、イベントの発生元参照に冪等性制約を設ける。今回確認できた1商品ID=現物1点の仕様では、`accounting_entries` に台帳イベント参照を追加したり、商品ごと1件の仕入会計明細の一意制約を変えたりする根拠はないため、現時点では提案しない。イベント台帳と既存会計明細は別々の責務として維持し、既存の会計明細・外部ID・同期履歴・照合状態を削除・上書きしない。

仕入現在値は既存`products`列で管理し、商品管理の更新経路からのみ変更する。仕入情報変更では、商品更新、変更イベント記録、未確定販売の利益再計算、出品中商品の見込み利益再計算を同一トランザクションで行う。現在庫はイベント残高を基準とし、互換投影値と在庫状態を同一トランザクションで更新する。具体的なDB列・インデックスを追加する前に、既存スキーマと会計CSV要件を確認する。商品ID間の原価配賦方式は設計対象外。

### 3.1 実装済みイベントテーブルの責務

`product_inventory_events`は追加済みの履歴テーブルであり、仕入現在値用の独立マスターではない。既存テーブル・カラム・インデックスを削除しない。

| 列 | 型・制約案 | 用途 |
|---|---|---|
| `id` | bigint primary key | イベントID |
| `user_id` | FK users, index | 所有者境界 |
| `product_id` | FK products, index | 現物1点の商品 |
| `event_type` | string(40) | 初回仕入、仕入情報変更、販売、取消、返品、在庫調整、移行時残高 |
| `quantity_delta` | signed smallint | -1、0、+1だけをサービスで許可 |
| `source_type`, `source_id` | nullable string(40), bigint | Sale・CSV取込等の発生元。直接入力イベントはnull |
| `idempotency_key` | char(64), unique within user | 同じ販売・取込・調整イベントの二重記録を防止 |
| `occurred_at` | timestamp | 取引・調整が発生した時刻 |
| `before_state`, `after_state` | nullable longText, Laravel encrypted-array cast | 仕入額、日付、仕入先、証憑・税区分・支払元等の変更前後。機微情報を平文保存しない |
| `actor_user_id` | nullable FK users, null on delete | 操作者 |
| `reason` | nullable text | 取消・返品・調整・訂正の理由 |
| timestamps | Laravel標準 | 記録日時 |

イベントサービスは `furimadeck` 接続の同一トランザクションで商品行をロックし、現在残高が0/1の範囲であること、適用後も0/1であることを確認する。現在庫イベントに応じて既存 `products` 投影値を同期する。仕入情報変更時は`products`の現在値が更新元となり、変更イベントにbefore/afterを記録する。Sale・外部CSVは既存のSale/Import行を発生元として冪等性キーを作る。初回の移行イベントは商品IDから決定的なキーを作り、再実行時に二重追加しない。

### 3.2 migrationの事前条件と検算案

1. migration開始前に、本番運用者が最新バックアップと隔離復元結果を確認する。
2. migrationは書込み前に、`purchase_quantity = 1`、`quantity_available IN (0,1)`、`inventory_status` と数量の一致、全Saleの数量が1であることを件数のみで確認し、逸脱があれば停止する。自動修正はしない。
3. 条件通過後、商品1件につき移行時残高イベントを1件作る。既存現在庫0/1をその時点の開始残高として記録し、過去のSale/返品を推測で再生成しない。仕入情報は現在値を暗号化スナップショットとして保持する。
4. 既存products/sales/accounting_entriesの件数、Sale原価スナップショット、販売・返品状態は変更しない。`accounting_entries` の一意制約にも触れない。
5. 移行後に、商品ごとのイベント数量合計が既存 `quantity_available` と一致し、移行イベント件数が対象商品件数と一致することを件数・合計のみで照合する。

本番の逸脱件数は未確認。ローカルで数量が1以外の商品・0/1外の在庫が0件だったことは、本番適用の前提を満たす証拠にはならない。

## 4. 既存データの移行案

1. 本番変更前に、運用者がDBバックアップの取得と隔離環境での復元を確認する。
2. 読み取り専用の事前検査で商品・販売・返品・会計明細の件数と数量整合性を記録する。PIIや秘密値は出力しない。
3. 各商品の現在の仕入スナップショットと現在庫から、切替時点の初期台帳記録を作る。
4. 過去の販売・返品を推測で再構成しない。既存Saleの原価・利益・会計連携状態は変更しない。
5. 台帳残高と既存 `quantity_available` の一致を検証してから、アプリの読取元を切り替える。
6. 既存の会計仕入明細、外部ID、同期状態、照合記録は削除・上書きしない。1つの商品IDに対して仕入会計明細を複数作らず、別個体の追加仕入は別の商品IDとして登録する。

移行件数や本番データの実値は未確認。現在のDBへの照会、移行、書込みはいずれも行っていない。

- 1商品IDは現物1点であるため、現時点では `accounting_entries` の商品単位1件の仕入明細制約を変更しない。既存の会計明細・外部連携・照合テーブルのキー構造も変更しない案とする。
- 現在の仕入情報は`products`既存列を使う。イベント台帳への移行時スナップショットは監査情報として保持し、仕入現在値を別途二重管理しない。

- 3.1〜3.2はイベント台帳migrationの設計・検査条件の記録である。開発DBへの適用は過去の確認で記録済み。本番の移行前検査、バックアップ復元、切替は未確認。

## 6. 切り戻し案

- 移行中も `products.quantity_available` と現行の仕入スナップショットを互換値として更新し続ける。
- 問題時は、台帳を読み取る新コードを戻し、旧アプリ版で既存の `products` 投影値を使って運用する。新しい台帳行やスキーマは削除しない。
- 旧アプリ版運用中はイベント台帳への書込みが止まるため、台帳コードを再度有効にする前に、切替後イベント・現在の投影値・Sale履歴を読み取り照合し、差分を記録する再同期処理を実施する。照合が終わるまで再有効化しない。
- 会計サービスへ送信済み・取込済みの状態を自動で戻さない。外部帳簿との照合を別途行う。
- 実DBバックアップからの復元は、事前に隔離環境で復元を確認した場合のみ運用手順に従って行う。

切り戻し時の新規台帳行の扱いと一意キーは、具体設計時に確定する。

## 7. 未決定事項

### 販売原価

販売対象の商品IDに記録された仕入原価を、そのSaleの原価スナップショットに記録する。同じ型番の他商品IDの原価を平均・FIFO配賦しない。FurimaDeck内の個別商品利益計算と、利用者の税務上の棚卸評価方法は同一と断定しない。

## 8. 実装後の検証項目

- 商品登録時の初回仕入記録と在庫残高
- 同一型番の別個体が別商品IDで管理され、仕入・仕入先履歴が商品ごとに保持されること
- 販売・CSV売上取込は1商品IDにつき1点だけ処理し、Sale原価スナップショットが当該商品IDの仕入原価と一致すること
- 数量2以上・部分販売入力が拒否されること
- 販売取消、返品（再入庫あり・なし）、在庫増減調整
- 競合する同時販売で在庫が負数にならないこと
- 商品・会計・分析画面の仕入、在庫、利益集計の一致
- 既存Sale、既存AccountingEntry、外部連携ID・照合状態が不変であること
- Free/Premium権限、所有者分離、CSRF、入力検証
- migration前後の件数・残高照合、失敗時の再実行安全性
